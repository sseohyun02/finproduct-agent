# 질문 검증과 상품군별 조회

## 실행 순서

1. CLOVA가 원문을 의도 JSON으로 변환한다.
2. `intent_validation.py`가 대상 이름, 연산자, 값, 상품군과 계산 조건을 검사한다.
3. 형식 오류나 정의되지 않은 조건은 오류 사유와 이전 JSON을 전달하여 한 번만 재해석한다.
   조건을 삭제해서 통과시키도록 요청하지 않는다. 재해석에도 실패하면 검색 실패로 안내한다.
4. `query_execution.py`가 각 상품군별로 시간 조건과 지원 범위를 검사한다.
5. 관계 조회 → 계산 조건 → SQL 필터 → 정렬 → 개수 제한 순서로 실행한다.
6. 실제 실행 기록과 조회값으로 답변을 구성한다. 최종 목록을 다시 LLM으로 재작성하지 않아
   표시 개수, 값, 미지원 안내가 바뀌지 않는다. LLM은 의도 해석에 사용한다.

LLM이 원문 조건을 완전히 누락하면 구조 검증만으로 모두 탐지할 수는 없다.
프롬프트에 조건 보존과 `unsupported_conditions` 기록을 요구하지만 실제 모델을 통한
질문별 평가도 필요하다. 모의 의도를 사용하는 단위 테스트와 실제 모델 평가는 구분한다.

## 입력 계약

```json
{
  "product_scopes": ["bond", "etf_domestic"],
  "graph_conditions": [
    {"relation": "sameGroupAs", "target": "신한은행", "direction": "reverse"}
  ],
  "sql_filters": [],
  "computed_filters": [],
  "sort": null,
  "limit": null,
  "limit_mode": "per_scope",
  "purpose": "group_exposure",
  "unsupported_conditions": [],
  "aggregation": null,
  "temporal": {"kind": "snapshot", "start_date": null, "end_date": null}
}
```

- `product_scopes`는 복수 상품군을 표현한다. 빈 배열만 상품군 불명확으로 처리한다.
- 기존 단일 `product_scope` 입력도 호환한다. 기존 `etf` 값은 국내 ETF 기본 계약을 유지한다.
  해외 상장 ETF를 요청하면 `etf_overseas`를 명시한다. 답변에 실제 조회 상품군을 표시한다.
- 공통 조건을 상품군마다 적용한다. 한 상품군에서 적용할 수 없는 조건은 해당 상품군을
  중단하고 이유를 표시하며 다른 상품군의 유효한 결과와 구분한다.
- `sameGroupAs`는 기준 회사를 포함한다. 기준 회사의 국적으로 대상 상품군을 바꾸지 않는다.
- 미지원 부정 조건, 최적화, 총개수 집계 등은 `unsupported_conditions`로 남긴다.
- 기존 테마 ETF 공통 구성종목 집계는 해당 테마 ETF **전체의 교집합**만 반환한다.

## 결과 개수

- `limit: null` 또는 누락: 상품군별 최대 3개. 실제 조회는 4개까지 수행하여 추가 결과를 판정한다.
- `limit: N`: 상품군별 최대 N개. 명시한 개수보다 적게 조회되면 있는 결과만 표시한다.
- `limit_mode: total`: 전체 N개를 요청한 상품군 순서대로 번갈아 배분한다.
  부족한 상품군의 몫은 다른 상품군에 배분한다. 상품군 간 통합 수익률/보수 순위가 아니다.
- 정렬 미지정: 상품코드순. 추천 순위가 아니라는 안내를 표시한다.
- 모든 필터와 계산 이후 정렬·개수 제한을 적용한다. 구성종목 조회도 기본 3개다.
- 안내문은 실제 표시 개수와 추가 결과 존재 여부로 생성한다.

## 비중 합산

```json
{
  "type": "holding_weight_sum",
  "companies": ["회사 A", "회사 B"],
  "operator": "lte",
  "value": 30,
  "unit": "percent"
}
```

임의 개수의 회사를 지원하며 별칭은 실제 회사 URI로 중복 제거한다.
모든 지정 회사를 보유한 ETF에서 해당 회사들의 Holding 비중만 합산하고 조건을 적용한다.
비중 누락·중복 속성·음수·비정상 숫자를 정상값으로 간주하지 않는다.

현재 로컬 원본은 `20 = 20%`인 percent 단위로 검증했다.
1,137개 시트의 열 구성을 확인했고, 365개 시트에서 시가총액 구성비×100과 저장 비중을
독립 대조했다. 원본에서 생성 대상이 되는 보유내역 26,528개와 현재 회사 그래프를
상품·회사·비중·중복 개수별로 전수 대조하여 일치를 확인했다.

KODEX200 원본의 삼성전자 33.03, SK하이닉스 30.01은 각각 33.03%, 30.01%다.
원본은 소수 둘째 자리 값이 float32를 거치며 미세한 오차를 갖는 것으로 확인했다.
검증된 정밀도(decimal_places=2)로 각 보유행 값을 복원한 뒤 합산하여 30% 경계에서
부동소수점 오차로 결과가 뒤집히지 않도록 한다.

검증 재실행은 프로젝트 루트에서 `python -m src.graph.verify_holdings`로 수행한다.
이 명령은 원본과 DB를 수정하지 않는다. 전수 대조 성공 시에만 회사 그래프의
원본 지문과 검증 JSON을 갱신한다. 원본/그래프 불일치 또는 단위 근거 부족이면 중단한다.
새로운 데이터의 단위를 단순히 숫자 크기만으로 추정하지 않는다.

검증 정보에는 다음 값을 기록한다.

- `weight_unit`: 원본이 30을 30%로 표현하면 `percent`, 0.3으로 표현하면 `fraction`.
- `source_sha256`: 확인한 실제 `etf_portfolio.xlsx` 파일의 SHA256.
- `evidence`: 원본 열과 단위 정의를 확인한 근거.

`build_ttl`은 재생성 시 원본 SHA256을 `HoldingsDataset.sourceSha256`으로 기록한다.
메타데이터와 그래프의 원본 지문이 일치할 때만 단위 변환을 허용한다.
원본 파일을 바꾸면 검증 정보도 다시 확인해야 한다. 단순히 기능을 켜려고 추정값을 기록하지 않는다.

## 적용 및 검증

이번 실행 정책·프롬프트 변경은 백엔드 서버를 재시작하면 적용된다.
DB 수정, 원본 재수집, 실제 LLM API 호출은 테스트에 필요하지 않다.
현재 원본과 그래프의 비중 검증 정보를 연결했다. 서버 재시작 후 % 합산 비교를 사용할 수 있다.
원본 변경 후에는 회사 TTL을 재생성하고 위 검증 명령을 다시 실행한다.

```powershell
python -m unittest discover -s tests -v
```

테스트는 임시 파일과 메모리 DB/그래프를 사용한다. 0~4개 결과, 명시적 개수,
복수 상품군·총개수 배분, 잘못된 관계의 1회 재해석, 미지원 조건 미실행,
시간 조건의 상품군별 처리, 비중 합산 후 정렬, 단위 지문 검증을 포함한다.
